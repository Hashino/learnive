## Objetivo e princípios

Learnive transforma qualquer tema, ideia ou problema que o usuário queira explorar em um currículo adaptativo, construído progressivamente como um **"livro vivo"** — um documento que cresce e se ajusta conforme a compreensão real do usuário é avaliada, em vez de entregar material fixo de antemão.

Princípios que devem guiar cada decisão de implementação (não são metas soltas — restringem como as features são construídas):

- **A sofisticação do sistema acompanha a do usuário** — calibração contínua e local (por conceito/objetivo) de ritmo e interesse, nunca um nível fixado uma vez.
- **Aprendizado é holístico, não atômico** — todo conceito novo se integra ao que já foi aprendido (ver exercícios de síntese/"integração" §8 e o grafo entre documentos §10).
- **Avaliação usa objetivos travados no momento da geração do conteúdo**, não julgamento posterior — evita a leniência natural de um avaliador sem critério pré-definido (§8).
- **Discordância legítima do usuário não é erro de compreensão** — o sistema confronta ideias dialeticamente, sem bajular (§7).
- **Conhecimento nunca é editado destrutivamente** — revisão gera novas versões, preservando a trajetória de aprendizado (§5).
- **O ciclo aprendizado → feedback é o mais curto possível** — geração em blocos pequenos e atômicos sempre que o conceito permitir, cada bloco terminando numa checagem de compreensão (§6).
- **A interação do próprio usuário é o sinal mais valioso** — o que pergunta, onde seleciona, o que erra realimenta diretamente o que vem a seguir; nunca é registrada como conversa lateral desconectada (§7).

## Architecture (from the spec)

**learnive** is a self-directed learning app: for each topic a user wants to explore it generates an adaptive "generative book" — a living document that is built incrementally, assesses real understanding at each step, and uses that to decide what comes next (including revisiting earlier concepts).

Decisions that constrain how features must be built:

- **Pedagogical base and cost discipline (SPEC §2.1, added 2026-08-21).** Which findings the app is allowed to build on, and what each mechanism may cost. Load-bearing, not motivational: **prior knowledge in the specific domain is the moderator that works — personality and declared preference are not**, and *learning styles are refuted*, so the profile must never produce "this user is visual, therefore a diagram" (choosing a diagram because the *content* is spatial is fine). Mechanisms are ranked by cost and that ranking decides what gets built: (1) **zero token** — arithmetic over the event log (review scheduling, scaffolding parameter, the evidence table) — always in; (2) **zero extra call** — a prompt addendum on a call that was happening anyway (interleaving, scaffolding fade, integration) — in; (3) **one extra call with a clear payoff** — a spaced review when an item comes due — in, because the call *is* the benefit; (4) **speculative call** — out, same reasoning that killed predictive prefetch (§14). Two signals in the old spec were **inverted and are now corrected**: §6.2 counted *questions asked* as evidence the material was too easy (it is elaborative generation, associated with better learning — and §7 calls the question the most valuable signal in the system, so both could not be true), and §7.1's psychological prose profile outranked behavioural evidence (now the weakest layer — it stays, inspectable and editable as before, but **evidence wins when they conflict**). New and never in the spec: **interleaving** (near concepts must be *distinguished*, distinct from integration's "distant concepts *combine*") and the **testing effect** reframing the exercise from gate to *intervention* — the retrieval instrument already exists as the `ask` move and already fires on every node, so this is about making it deliberate, not about generating more graded exercises. PLAN.md S23–S25 implement all of it; nothing already built is removed.

- **Topology (§3):** Rust backend as a *local HTTP server* (`axum`), rendered in the user's real browser — not a Tauri/Electron webview. The backend does all filesystem I/O; the browser never touches the filesystem, only talks to the backend over localhost. Main content flow is server→client via **SSE**; user actions (select text, ask, answer) are ordinary HTTP requests.

- **Frontend = minimal vanilla JS, no framework and no build step (§3).** No JS VDOM framework (React/etc.): the canonical data *is* the HTML dialect (§4.2), so a JSON-state VDOM is impedance — the server generates the dialect, the client displays it. Assets embedded in the binary (§15 portability). **Divergence from SPEC §3, deliberate and verified — do not "fix" it back:** the spec names HTMX as the backbone and a shared-Rust **wasm** anchoring module; both were dropped 2026-08-03 (recorded in PLAN.md's loop-front checklist with the evidence). HTMX doesn't fit the flow that actually got built — content streams over **SSE-on-POST**, because `EventSource` can't carry the session token and §3.1 forbids GET mutation, while HTMX's SSE extension assumes `EventSource`/GET. The wasm module has no consumer: `Content::resolve` is called once, server-side, and the client never resolves anchors (interactions render as cards in a separate panel, not as inline highlights), so there is no JS reimplementation to keep in sync. `crates/core` stays tokio/axum-free anyway — cheap, and keeps the option open.
- **No emojis anywhere in the front end (user decision, 2026-09-01).** Not in badges/status glyphs, not in button/label text, not in generated UI copy — `assets/*.js`/`assets/*.css`/`index.html` stay emoji-free going forward. Came from removing the sidebar's 🔒 lock badge on a locked outline item (the row's own non-clickability and CSS dimming already communicate "locked" without a glyph); the rule generalizes past that one badge to the whole front end, not just outline state icons. Plain Unicode symbols already load-bearing elsewhere (✓ for demonstrated, ⚠ for a chapter that failed TOC matching) predate this rule and are not itself an emoji-removal target — the rule is about not *adding* more, not stripping every existing glyph on sight.

- **Local-server security is mandatory, not optional (§3.1):** the server holds the user's API keys and is reachable by any browser tab, so it must defend against CSRF/DNS-rebinding. Bind only to `127.0.0.1`; require a session token on every request (Jupyter-style); strict `Origin`/CORS validation (never `*`); no state-changing endpoint responds to GET.

- **Storage is human-readable files, no binary DB (§4), Obsidian-style.** HTML for living documents (generated content + user annotations), PDF for immutable source books. Directory layout is only for loose human navigation — real graph relationships (prerequisite, cross-reference) live as `[[links]]` *inside* content, never implied by file position. One HTML file per concept node, inside one directory per living document.

- **App-specific HTML dialect (§4.2):** generated HTML uses a semantic tag/attribute convention (node IDs, version-chain pointers, learning-objective tags on spans, user-annotation spans, source-citation markers) — parse it in Rust via `html5ever`/`scraper`/`lol_html`, not ad-hoc string handling.

- **Data model is a versioned concept graph (§5).** The reading order shown to the user is a *linearization* (traversal) of the graph and can be re-planned as the graph changes. **No destructive edits:** revisiting an old concept creates a *new version node* in that concept's chain; the original node stays intact so user annotations remain anchored. Outside this revision mechanism the system only moves forward (incremental generation from the current reading point, never in-place rewrite).

- **Node file = two layers (§4.3).** A **content layer** frozen at creation (prose, objectives, exercise, citations; every block has a stable `data-block-id`) plus an **append-only interaction layer** (annotations, Q&A, remediation) that *references* content IDs and never mutates them. This resolves the §5-immutable vs §9-"AI edits the document" tension. Anchoring is by stable block ID (survives streaming/regen because content is frozen), with fuzzy quote+prefix/suffix for sub-block selections. The reading-highlight line is ephemeral client UI state, **not persisted**. A v0 tag/attribute vocabulary is sketched in §4.3 — treat it as the concrete data contract to nail down first.

- **Generative interactive HTML, always sandboxed (§4.4).** Full use of generated HTML: content can include bespoke **interactive visualizations** when they teach better (not just prose rewrites of sources), and exercises are **not limited to checkbox/textbox**. Strategy chosen: **arbitrary LLM-generated JS, always sandboxed** (no fixed component library). Two invariants this must respect: (1) **Security (§3.1)** — generated JS never runs in the app origin; it renders in a `<iframe sandbox>` with no same-origin/token access and reports back only via a narrow validated `postMessage` channel. (2) **Gradeability (§8)** — an interactive exercise must emit a **structured answer artifact** via `postMessage` whose schema is generated *together with* the rubric and locked *before* submission; the rubric grades the artifact, so interactivity never becomes eyeballed grading. Interactive blocks are frozen content-layer elements with stable `data-block-id` (§4.3); their internal fiddling is ephemeral client state (only the answer artifact is persisted). Heavier widgets hydrate after prose so they never hurt TTFT (§14).

- **Assessment rubric is locked at node-creation time (§8),** generated *together with* node content, to avoid LLM-as-grader leniency. Every "application" objective includes at least one item requiring transfer to a scenario *not* covered by the node text. Grades are per-objective `{not demonstrated, partial, demonstrated}`, not pass/fail; exercises are grounded in the same source material (§8) — clean for exact sciences, looser elsewhere.

- **Failure → remediation conversation (§8.2), not silent retry.** On a failed check, the node opens a tutor conversation in its interaction layer: explain the concept *in the exercise's context* (worked example / step-by-step of the failed problem), then propose a new similar problem whose similarity to the worked example **increases with each successive failure** (scaffolding converges toward the demonstrated solution, then difficulty ramps back up). Which explanation finally landed is high-signal for the profile (§7). Next node only fires once the objective is `demonstrated`.

- **Cold start (§6.1):** one generic prompt ("O que vamos aprender?") + textbox. The agent decides from the input whether to start the living document directly or open a scope-negotiation conversation until the outline is defined.

- **Abstraction calibration is the concrete hook for §2 (§6.2).** Signal = error+question rate per concept. Advancing with no errors/questions ⇒ abstraction too low ⇒ richer language, more superficial explanation, harder exercises (within-move and cross-node integration alike). Inverse when struggling. Continuous and local per concept, driven by the profile (§7), parameterizes generation (§6). *("atomic" exercises dropped from this bullet's wording 2026-08-23 — the atomic unit moved from the node to the move within a node, §6.3.)*

- **User-profile / pedagogical-trajectory memory (§7)** accumulates from all interactions. Two behaviors to actively enforce against default LLM tendencies: (1) be *adversarial* — build the strongest counter-argument to the user's position rather than mirroring/flattering; (2) distinguish legitimate disagreement from failed comprehension. Text-selection-plus-question is the highest-signal input and must directly steer the next generated node, never be logged as disconnected side chat.

- **Long-term memory architecture (§7.1)** — the profile is NOT a replay of all interactions. Event-sourcing split: an **immutable append-only event log** (source of truth on disk, never fully loaded) vs. a **materialized profile projection** (compact, curated, the thing actually fed into generation). Multi-resolution (recent verbatim → mid-term summaries → distilled traits + per-concept retention); retrieved by relevance (reuses the §10 layer), not loaded whole. Profile beliefs are timestamped and **decay/revise** — reuse the §5 "new version, non-destructive" pattern for beliefs about the user, not just concept nodes. The profile is **user-inspectable and editable** (human-in-the-loop is the cheapest fix for drift/bad compaction). Residual risk is calibration of lossy compaction, not scale; the immutable log makes compaction errors recoverable, the inspectable profile makes them correctable.

- **Files are the source of truth; indexes are rebuildable derived caches (§4, §10, §7.1).** Retrieval at scale needs a binary index (embedded vector store / sqlite) — this does NOT violate the "no proprietary DB" stance because the index is always reconstructible from the files; deleting it only forces reindex. Same retrieval layer serves both cross-document context (§10) and profile memory (§7.1).

- **Source grounding: local file library today; the acquisition ROUTE reopened 2026-08-30 and is the biggest open decision in the project (§11, §11.1's banner, §15, §16, PLAN.md S27).** Two mutually exclusive routes, stated by the user and deliberately not resolved: **(A)** LibGen/Sci-Hub fills the primary slot — a seamless automagic flow, the best possible UX, but it forecloses legal monetization, which matters again now that §15 admits a hosted product; **(B)** manual acquisition only (today's behavior) — legally clean, but ~30 minutes of tedium per curriculum, and *"in the end for 99% of the cases they'll be downloading from LibGen/Sci-Hub either way"*, so route B moves the unauthorized download to the user rather than removing it. **Whichever wins, the consequence is the same and it is load-bearing: if it's B, the app must be near-perfect** — half an hour of chores only pays off if what follows clearly beats reading the book alone, which raises the bar on the acervo gate, PDF↔item matching, and chapter resolution from "usually works" to "does not waste the investment the user just made." Deleting route A's code would decide the question by omission, which is why `Source::LibGen`/`Source::SciHub` stay and S28 does not remove them. Everything below describes route B, the behavior that ships today. Node content is grounded in real sources cited by book+chapter/page or article — and the source of explained substance is **never the LLM**, in any move that explains (node generation, tutor questions, remediation): no source coverage means no generation, not model prose with a disclaimer. Origin was deliberately left open 2026-08-23, then closed: the user supplies PDFs into a global local library (`<data>/library/`); the app never fetches or downloads a source. The only network calls left for sources are **metadata-only existence checks** (OpenLibrary/Crossref/OpenAlex/arXiv) before a proposed book/article enters the reading list — never a content fetch. A new cold-start step, the **acervo gate**, validates the library (presence, identity, text layer, table of contents, page map, retrieval index) before generation is allowed to start. **Format: PDF is the sole canonical format** (reversed 2026-08-23 — previously EPUB > PDF > DJVU). Ingestion keeps the **original PDF intact** as the canonical artifact; extracted text is index-only (grounding/citation/retrieval), never rendered for display — display is always the real PDF in the browser's native viewer (§11 below, PLAN.md S27j — not yet built). Per-node source selection is now **structural**, not agent-ranked: a node is born from a specific chapter during contextual outline expansion, so it already knows its source.

- **The living document is the only place for user notes (§9, §11).** The source viewer is **read-only** — no annotation on the source (it's immutable). Selecting text in the source is interaction, not a persistent mark: it routes into the living document (inserted/answered there, already cited by book+chapter). This keeps a single notes store and ensures user marks stay high-signal for §7, never trapped on a static source. Because the viewer is read-only, EPUB's reflow view has no downside — no need for a pixel-faithful page.

- **AI provider is bring-your-own (§12).** OpenRouter OAuth PKCE is the default path; direct Anthropic/OpenAI and OpenCode Zen are BYOK. Do **not** build on subscription OAuth tokens (Claude Pro/Max, ChatGPT Plus). Keys are stored in a local `0600` `<data>/secrets.json` behind the swappable `SecretStore` facade — **not** the OS keychain (user decision; the keychain stays a future variant for a desktop build). The invariant that matters is unchanged: never a centralized DB.

- **Model tiering, set up by intent not by model name (§12.1).** Two tiers — a light/fast model for frequent cheap tasks (exercise generation, grading against the rubric, summaries, embeddings, cross-ref decisions) and a robust model for explanatory prose and adversarial confrontation. Non-technical users never pick two models by name: the app ships maintained recommended pairings per provider/tier, and setup asks one high-level intent question (free vs paid) that derives both tiers. Manual two-model config is an optional advanced override; if only one model is available it serves both tiers (**tiering is an optimization, never a barrier to start**).

- **Latency is a UX/architecture problem, not a model problem (§14).** The app must be pleasant on today's autoregressive API models; a faster model (e.g. diffusion LLMs) is a future, non-load-bearing lever available only once the stack is self-hosted. Target metric is **time-to-first-token / time-to-reading (~1s)**, not time-to-complete. Levers: stream token-by-token so reading outpaces generation (§3); pipeline prose vs. exercise+rubric (rubric must be locked before submission, not in the same call, §8); model tiering (§12.1); optimistic UI. **Predictive prefetch was dropped (2026-08-03)** — it assumed the next node was predictable from the outline, which stopped being true once `decide_move` became dynamic, `plan` could rewrite the outline, and the graph gained prerequisites; speculating on a speculation spends the user's money under BYOK. Do not reintroduce it for prose; a retrieval-only prefetch (embeddings for the next unlocked item — deterministic, no model tokens) is the only form left on the table. Treat the model backend as a **swappable, per-subtask-routed knob**, not a dependency. Atomic nodes (§6) mean more round-trips — these levers are what make that density affordable.

- **Cost control (§12.2) still applies; endgame (§15) is a POSSIBILITY again (revised 2026-08-30).** BYOK + deliberately token-heavy → user sets daily/weekly/monthly spend caps and sees running spend; hitting a cap degrades before it blocks — warn, force the fast tier (§12.1), then pause generation. **The 2026-08-23 "no more commercial endgame" is partially reverted.** The shape the user stated: finish the app → give it to broke college friends → organic spread → **and then possibly** a subscription hosted web version on frontier models (their guess: GLM 5.3 / 5.3 Flash). It is a possibility, not a dated plan — nothing may depend on it happening, nothing may block it. **No desktop-webview step**: localhost until a 1.0, then straight to hosted web; Tauri/Electron are out for good, so §12's OS-keychain `SecretStore` variant has lost its only future consumer — don't build it.
  - **The design consequence that outranks the rest: free models are the product target, not a floor to tolerate.** The seed audience is students who can afford exactly the free tier. Measuring against a small model is therefore the *real* case — never read "small model did badly" as "acceptable, real users will have better." Frontier models only ever appear in the paid hosted tier, if it exists.
  - **Operational corollary, measured 2026-08-30** (`docs/S27g-chapter-matching-measurements.md`): free tiers `429` constantly — 3 of 6 probes died mid-run on `FreeUsageLimitError`. So **any recovery path that spends an extra model call is broken exactly when it is needed.** Failure recovery must cost **zero tokens**: ask the user, or use data already on disk. This is a hard constraint on design, not a style preference.
  - Still true from the 2026-08-23 wording: local-first, portable files as source of truth, and the swappable acquisition module were kept because they're good design, not because a product needed them — that doesn't change, they just stop being the *only* justification. Multi-device sync and paying-user cost visibility regain a possible consumer but no priority. Licensing (the AGPL+CLA question dropped in 2026-08-23) reopens for the same reason — **and it is now coupled to §11.1's unresolved acquisition route.**
  - **§11.1's source-origin question REOPENED 2026-08-30** and is the biggest open decision in the project. Two mutually exclusive routes: **(A)** LibGen/Sci-Hub in the primary slot — a seamless automagic flow, the best possible UX, but it forecloses legal monetization, which now matters again because §15 does; **(B)** manual acquisition only (today's behavior) — legally clean, but it costs the user ~30 minutes of tedium per curriculum, and as the user put it, *"in the end for 99% of the cases they'll be downloading from LibGen/Sci-Hub either way"* — route B doesn't remove the unauthorized download, it moves the action to the user. **The design consequence, whichever route wins: if it's B, the app has to be near-perfect** — half an hour of chores only pays off if what follows is clearly better than reading the book alone, which raises the bar on the acervo gate, PDF↔item matching, and chapter resolution from "usually works" to "does not waste the investment the user just made." This is *why* `Source::LibGen`/`Source::SciHub` stay in the tree and S28 does not remove them: deleting route A's code would decide the question by omission. **§16 tracks open decisions/risks** (this one, concurrency baseline, grounding in non-exact domains, evaluator-failure telemetry, sync) — consult before building in those areas.
